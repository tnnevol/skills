# 用户指南：插件索引、定时提醒与对外部署

本页覆盖用户可感知的功能：插件索引（0.2.2 起由「插件市场」改名）、宿主级定时提醒、反向代理部署，以及 rc.3 的 DeepSeek 模型列表行为。其余上游变更（`persistence-changes/`、`upgrade-guide/`、`defensive-patterns/` 等）属内部工程文档，需要时直接读子模块 `sources/dsh/docs/`。

## 插件索引（Plugin Index）

> 0.2.2 起「插件市场」统一改称「插件索引」：实验性 bundle 叫「自定义插件索引」，界面文案也改成索引；`plugin_market` 工具名和 JSON 文件格式保持不变。旧文档里的「市场」字样按索引理解。

插件索引是一个 JSON 文件，列出可安装的 DSH 组合包及其标题、图标、作者和版本。

### 打开「发现」

打开**插件** → 在**实验性插件**下找到**自定义插件索引**并打开开关。**已安装**旁会出现**发现**标签页，Creator 模式还会获得只读的 `plugin_market` 工具。关闭该组合包会再次移除这两者。

DSH **不内置任何索引源**。选择**发现** → **添加索引源** → 输入索引文件 URL。

索引 URL 的约束：

- 必须使用 `http:` 或 `https:`
- **不能包含用户名、密码或 `#` 片段**
- 每个索引源属于当前 profile

> ⚠️ 网络路径上的任何人都能修改 `http:` 索引（包括其中列出的安装 spec），因此**经由不受你控制的网络访问的索引应使用 `https:`**。

### 浏览和安装

- 工具栏左侧的索引菜单用于切换索引源，并可打开**管理索引源…**，其中每个索引源显示最近一次的错误。
- 搜索匹配名称、作者、关键词，以及**所有语言**的标题、描述、分类和标签，并容忍拼写错误；在你选择其他排序之前，结果按最佳匹配排序。
- **标签**菜单、分类按钮和**排序**菜单使用索引声明的分类、标签和排序键；**发布时间**按每个插件最新版本的时间排序。

每张卡片显示插件的推荐版本：**与当前运行的 DSH 兼容、且不是预发布版本的最高版本**；插件没有列出任何非预发布版本时，则是兼容的最高预发布版本。

**安装**会打开确认框，显示该版本的来源（npm 包和注册表，或 Git 仓库、提交和目录）。确认后开始常规的插件安装，包括其中的兼容性检查和注册表检查；**未经确认不会安装任何内容**。

选择卡片会打开插件页面。**版本**列表显示列出的每个版本及其兼容性，并为 DSH 接受的任何版本提供**安装**，包括旧版本和预发布版本。

> ⚠️ **索引是第三方内容。** 每个插件的标题、描述、图标、作者和来源都由索引决定；**DSH 只检查文件格式，不验证这些声明**。只添加你信任的索引源，并在安装前核对确认框中的来源。

### 发布索引

索引是 UTF-8 编码的 JSON 文件，默认不超过 **128 MiB**，以 2xx 状态码返回且**不经过重定向**。放到任意静态主机即可（GitLab Pages、GitHub Pages，或通过 https 访问的对象存储）。

图标可以内联也可以是单独文件：

- **内联图标**：索引中的 base64 `data:` URL，不需额外请求但会变大
- **单独图标**：一个 URL。**相对图标相对于索引 URL 解析**（与网页中图片相对于页面解析相同）。指向其他源（协议、主机、端口）的绝对图标 URL **必须使用 `https:`**

最小索引（一个 npm 插件 + 一个来自 Git monorepo 的插件）：

```json
{
  "format": 1,
  "title": { "en": "Team plugins", "zh": "团队插件" },
  "plugins": [
    {
      "name": "dsh-plugin-foo",
      "title": "Foo",
      "description": "Adds the foo tool",
      "icon": "icons/foo.svg",
      "author": "Jane Doe",
      "homepage": "https://github.com/jane/dsh-plugin-foo#readme",
      "repository": { "url": "https://github.com/jane/dsh-plugin-foo" },
      "versions": [
        { "version": "1.1.0", "publishTimestamp": 1790476800, "source": { "type": "npm" }, "engines": { "dsh": ">=0.2.0-rc.2" } },
        { "version": "1.0.0", "publishTimestamp": 1788000000, "source": { "type": "npm" } }
      ]
    },
    {
      "name": "@team/dsh-bar",
      "versions": [
        {
          "version": "0.3.0",
          "publishTimestamp": 1789000000,
          "source": {
            "type": "git",
            "url": "https://gitlab.example.com/team/dsh-plugins",
            "commit": "3f9c2e1d8a4b6c0e7f1a2b3c4d5e6f708192a3b4",
            "path": "packages/bar"
          }
        }
      ]
    }
  ]
}
```

标为 `LocalizedText` 的文本字段是字符串，或以小写语言 id 为键的字符串对象（如 `{ "en": "Foo", "zh": "甲" }`）；**对象必须包含 `en`**。DSH 不认识的成员会被忽略。

违反任何一条规则时，**DSH 会拒绝整个索引**，并在「管理索引源…」中该索引源下方显示原因及**违规值的 JSON 路径**。

### 用参考生成器生成索引

上游仓库包含参考生成器，可从一份纯文本列表构建索引。每行写一个 npm 包名或 https Git 仓库 URL；空行和以 `#` 开头的行会被忽略：

```text
@team/dsh-foo
https://gitlab.example.com/team/dsh-plugins
```

```sh
pnpm --filter @deepseek-ai/dsh-plugin-market-generator start \
  --input plugins.txt --output site/index.json --title "Team plugins"
```

- **npm 包**：索引列出所有未弃用、**未设为私有**且声明了 `dsh.bundle` 的版本
- **Git 仓库**：在默认分支上查找 `package.json` 没有设置 `"private": true` 的组合包，列出 `vX.Y.Z`、`X.Y.Z` 和 `<name>@X.Y.Z` 标签处的版本，以及每个包在默认分支上的版本
- 标题、描述、图标、作者和主页取自每个插件的**最高版本**

> ⚠️ 生成器**只下载和读取文件，从不安装包或运行其代码**。它在列表旁的 `.plugin-market-cache` 中保存缓存，再次运行时只下载新的版本和提交。

发布时把 `index.json` 及其 `icons/` 目录并排放到静态主机即可。

## 定时提醒（Schedule，0.2.2 起语义改为重复规则）

宿主级 Schedule 由随包可选 bundle「自动化任务」（`@deepseek-ai/dsh-experimental-schedule-bundle`）提供，默认关闭；发布的 Web profile 自带宿主 Schedule 服务与「自动化任务」页面。

### 四个工具（0.2.2 改名）

| 工具 | 职责 |
| --- | --- |
| `schedule_create` | 创建提醒：名称、指令、开始时间、一条 RFC 5545 重复规则、投递目标 |
| `schedule_list` | 列出所有对话的提醒，活动提醒在前 |
| `schedule_view` | 按 id 读取一条提醒 |
| `schedule_edit` | 修改、暂停、恢复、删除提醒；修改保留 id 与已保存的投递记录 |

- **`schedule_update` 与 `schedule_delete` 已不存在**，统一由 `schedule_edit` 承担，不要再按旧名字调用。
- `standard`、`cordis`、`ptc` 三个 preset 声明这四个工具和时钟上下文；`minimal` 两者都不声明。
- 被委派的 subagent **能看到**这四个工具，但每个工具都会拒绝来自被委派 subagent 的调用。

### 重复规则与投递目标

提醒由一条 RFC 5545 重复规则驱动（例如每个工作日 09:00，或仅一次），开始时间用 UTC 或某个 IANA 时区表达。投递目标三选一：

1. **当前对话**
2. **首次投递时创建一个新对话**（之后沿用）
3. **每次投递都新建对话**

新对话使用当前对话的工作目录与 preset，并加入在其工作目录注册的 Workspace，标题取提醒名称；每次新建对话的提醒标题还写出该规则时区下的启动时间，例如 `Weekday digest · 2026-10-12 09:00`。

同一提醒的每次投递之间至少间隔一分钟（相对上一次计划时间或上一次「立即执行」）；每次新建对话的提醒改为等待宿主的**最小运行间隔**，默认一分钟。延迟投递（例如宿主重启后补投）不会推迟下一次投递。

### 手动创建与页面操作

不经模型创建：从侧栏打开「自动化任务」页 → **新建**旁的**选择创建方式** → **手动创建**（尚无任务时直接点**新建自动化任务**）。编辑页字段为「自动化任务名称」「自动化任务内容」「执行位置」「关联工作区」和「运行时间」：

- **执行位置**：「新建对话并复用」（默认）或「每次新建对话」。
- **关联工作区**：列出每个已注册 Workspace 及其目录；初始值为「默认工作区」，无默认时取第一个；没有任何 Workspace 时显示「未分组」并使用宿主项目目录。
- **运行时间**：初始为「仅一次」，浏览器时区下一小时后。

页面可跨 Session 查看、按「任务状态」（全部 / 已开启 / 已暂停 / 已结束）过滤、**立即执行**、**暂停任务** / **恢复任务** 和**删除任务**。删除会连同已保存的发送记录一起移除，但**不会删除相关对话**。任务详情底部有「关联会话」或「最近运行对话」，可跳到投递目标。

### 时间与投递的事实边界

- Session 未打开时提醒仍然保存；宿主运行期间到期会恢复或创建目标 Session 并排入 follow-up，不中断当前工作。
- 重启后补投逾期的一次性提醒，或每条重复提醒最近错过的一次。
- **已保存的发送记录只证明消息已持久化到对话收件箱，不表示模型完成了工作**，也不是执行历史或外部通知渠道。
- 投递不保证恰好一次：收件箱持久化后崩溃或任务写入失败，可能留下未记录的已投递消息并重复投递。
- 关闭宿主会丢弃仍在对话收件箱中等待的消息（记录保留、模型收不到、也不会重发）。
- 已删除的任务记录不会被重建；只记录在旧 Session 日志里的提醒不会自动调度，需要时重新创建。
- 历史保留按 `deliveryHistoryDays` / `deliveryHistoryRecords` 裁剪，最近一次回执始终保留。

### 排错

| 现象 | 检查方向 |
| --- | --- |
| 提醒工具不可用 | 插件管理页「官方」分组启用「自动化任务」bundle；或在 profile 的 `dsh.profile.bundles` 中选中它 |
| 工具名不存在 | `schedule_update` / `schedule_delete` 已改名，用 `schedule_edit` |
| `patch: entry schedule not found` | profile patch 仍按 id 覆盖已被 bundle 接管的旧组合行 |
| 任务已暂停/已结束却不再投递 | 这是预期行为；用「立即执行」可手动投递一次 |

## 在反向代理之后发布 Web UI

`dsh --profile web` 在 **loopback 端口**上提供 GUI，因此其他机器上的浏览器无法访问它，进程也无从得知你实际使用的地址。它前面的反向代理拥有这条外部链路——公开主机名、TLS，以及转发到监听器之前剥离的路径前缀——而 `--public-url` 则告诉 DSH 浏览器使用的是哪个地址：

```sh
dsh --profile web --public-url https://app.example/ui/ --trusted-host app.example
```

### `--public-url` 公告什么

`--public-url` 接受可带挂载前缀的 `http://` 或 `https://` 根，并把它**归一化为以 `/` 结尾**。它提供：

- 打印与打开的启动 URL
- `DSH_WEB_URL`
- agent 运行时上下文中的 Web GUI URL

webserver 继续提供 **origin-root** 路由，且从不了解挂载。`publicUrl` 配置字段发布同样的公告。

### 代理必须做什么

- **保留浏览器可见的 `Host`。** 栅栏把收到的 `Host` 与被接受的 authority 比对，因此代理应**原样转发**，不要改写成监听器的地址。
- **剥离挂载前缀。** 监听器应答的是 origin-root 路由，因此对 `/ui/api/...` 的请求必须以 `/api/...` 抵达。
- **转发升级请求。** 页面发出的每个请求与 **WebSocket 升级**都必须连同其 `Upgrade` 与 `Connection` 头抵达监听器；代理对外提供 HTTPS 时，**TLS 在其外部链路上终止**。
- **改写 cookie 作用域。** 以明文 HTTP 提供服务的后端签发不带 `Secure` 的 host-only `Path=/` cookie；代理再把 `Path` 改写为挂载（`/ui/`），并**仅在其 HTTPS 链路上添加 `Secure`**。监听器自身提供 TLS 时 cookie 已带 `Secure`，代理只需改写 `Path`。
- **重定向裸挂载。** `/ui/` 是**唯一入口**：只有它把启动 token 换成会话 cookie；已持有该 cookie 的浏览器可由它或 `/ui/index.html` 取得文档。对 `/ui` 的请求必须以 `/ui/` 抵达。

### 信任浏览器使用的 authority

栅栏接受 loopback、监听器自身的绑定地址，以及每个由 `--trusted-host` 点名的 authority。浏览器若以其他任何 authority 访问部署，**无论代理多么正确，每个 API 调用都会得到 403**。

> ⚠️ 请用 `--trusted-host` 点名**浏览器可见的** authority；用 `--public-url` 公告它**只是展示，并不等于接纳**。不带端口的条目匹配任意端口，适合每次绑定不同端口的隧道。

栅栏只放行请求；**打印 URL 中的启动 token 与签名会话 cookie 才完成认证**。无论 TLS 在哪里终止都不改变这一点：证书只是向浏览器标识服务器，而不是向服务器标识浏览器。

> ⚠️ 无论是公告 URL 还是栅栏都**不保护监听端口本身**，请把端口限制在可信代理或网络内。

### 在监听器上终止 TLS

传入 `--tls-cert` 与 `--tls-key`，两者各是**相对进程工作目录解析**的路径：证书文件包含完整证书链，密钥文件为**不带口令**的 PEM 私钥。

- DSH **从不获取、续期或监视证书**，且载体**只读取一次文件**——更换文件后需重新加载监听器或重启进程
- 文件缺失或无效时**启动失败，绝不回退到 HTTP**
- 浏览器使用自己的信任库与名称校验，因此证书必须覆盖你所访问的 hostname 或 IP
- 默认端口仍为 **3080**
- 原生 TLS 不需要代理，但代理部署与 `--public-url` 仍分别受支持

TLS 监听器会给会话 cookie 加上 `Secure`；**公开部署的浏览器侧链路应保持 HTTPS**，才能让浏览器回传这些 cookie。

### 保护外部链路

可以在代理处、监听器本身或两者上终止 TLS；`--public-url` 仍只是公告。面向浏览器的 `http://` 根会**明文暴露启动 token**。

> ⚠️ 打印的 URL 携带进程凭据，**只应与预期用户分享**。

### 对应配置位置

| 命令行选项 | 配置位置 |
| --- | --- |
| `--public-url` | Web profile 的 `web-runtime` 行 `publicUrl` |
| `--trusted-host` | `Connection` 行 `trustedHosts` |
| `--tls-cert` / `--tls-key` | `webserver` 行 `tls` |

## DeepSeek 模型列表跟随官方发布（rc.3 起）

保存密钥且使用默认端点时，DeepSeek 的模型不再固定为内置清单，而是**跟随 DeepSeek API 发布的列表**：

- 第一次需要模型时加载列表，使用期间约每十分钟在后台刷新一次；无法加载时退回内置模型。
- 使用发布的列表时，**设置卡片上显示的是内置模型**，因此新发布的模型只会出现在模型选择器中——卡片和选择器不一致是预期行为，不是 bug。
- 在**自定义设置**里编辑**模型目录**后改用你自己的列表，不再跟随发布列表；点**恢复默认模型**重新跟随并重新加载。
- 账号路由与 API key 路由共用同一套列表配置（`ModelListingConfig`：加载超时、刷新年龄、`modelOverrides`），两种路由行为一致。

排查「模型列表为空」时，先确认当前是跟随发布列表还是自定义目录：自定义目录下要检查适配器协议、`baseURL`、凭据和发现接口；跟随发布列表时则要检查实例能否访问 DeepSeek API。

## 模型目录的探测与排序（0.2.2 起）

在**设置 → 模型 → 模型目录**中改交互有两处变化：

- **获取可用模型**（探测）：响应打开的可搜索选择框会**默认勾选列表中已有的模型**。搜索后勾选要添加的模型、取消勾选要移除的模型，再点**更新列表**；按钮文案从「添加所选」改成「更新列表」。**端点未列出的已配置模型保持不变**，不会被探测结果清空。
- **调整顺序**：编辑提供商 → **自定义设置** → 拖动模型的三横线手柄即可调整该提供商内模型的顺序（也可聚焦手柄后按上下方向键）。保存保留顺序，取消放弃修改；**模型选择器按该提供商保存的顺序列出模型**。

探测只是便利手段而非保证：探测失败或列表为空时手动添加模型 ID 效果相同。内置提供商一律由已安装目录作答，即使其 API 地址指向网关；要看网关实际提供的模型，请通过自定义提供商探测。
